# 匹配验证集是否可行（零拟合）预登记

日期：2026-10-05。规范：`configs/validation_match/SPEC.json`。实施：`scripts/validation_match.py`。候选回传沿用 `configs/slot_screen/SPEC.json` 的 23 份已评分收据。

## 用户问题

"能否通过寻找一份和测试集分数相近的验证集合"——即：能不能挑出一个本地验证集，使它的分数与平台 322 行分数同步，从而在本地筛选候选。

## 拆成三个可判定子问题

**A. 测试侧、无权结构（322 个自由行权重）。** 平台的 322 行分数对候选的响应，一阶近似是改变向量 Δ 的固定线性泛函：`平台增量 ≈ Σ_j w_j Δ_ij`，`w_j` 由该行残差符号决定，唯一但不可见。23 份收据给出 23 个方程，未知数 322×2。用最小范数最小二乘拟合 `w`，再做**留一候选**预测：只用 22 份拟合，预测第 23 份的平台增量。若留一误差不低于"预测 0"，则 `w` 不可识别。

**B. 测试侧、规则化权重。** 同样的问题，但把行权重限制在一个小的先验基上（常数、相对水平、铁口、预测分位），即"用一条规则挑出匹配的行"。时间列 17 份 vs 7 个基权重，可识别。若留一误差不低于零基线，则不存在这样的规则。

**C. 本地侧、分数水平匹配。** 用已记录的 OOF 列（`ema-silu-20261004/development-r1/oof-s42,s3407.npz`，含 incumbent 时长列 `reference`、铁量列 `iron`、候选 `SILU_A100/A20` 与 2754 行标签），从 2754 行中无放回抽 322 行（20000 次），得到：
1. 子集上 incumbent 的分数分布范围与"落在平台水平 96.3979 ± 0.02 内"的比例；
2. 在这些**水平匹配**的子集上，候选增量的分布；
3. 子集水平与候选增量之间的秩相关。

若水平匹配能带来筛选能力，则 (3) 应显著非零、(2) 应收窄并能复现平台判定（SILU_A100 平台 −0.0247）。

## 预算与边界

- 零拟合、零新包、零桌面写入、零上传；只读已记录 OOF 列与已评分提交包。
- C 的子集复用基模型在其他折见过的行，不是独立留出集；本实验只测"水平敏感性"，不当作独立验证。
- A、B 都在同一批 23 份结果上拟合，留一虽有交叉验证形式，但收据之间共用 incumbent、共用 322 行、集中在同一时间段，**不是独立样本**；任何"看起来可预测"的结果都只是前瞻假设，必须在下一份候选上传前先记录预测再核对。
- 不预报平台分数，不改历史决定，不关闭模型家族。
